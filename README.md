# Echo — Social Mention Intelligence

Echo monitors your keywords across **X (Twitter)**, **Reddit**, the **open web** and the **press** and surfaces buyer-intent mentions into a single feed. Scheduled sweeps score each mention for intent, filter it against your threshold, and drop the matches straight into your dashboard.

---

## 🚀 Features

- **Onboarding** — 4-step flow collecting name, website, core offer and keywords, with AI-suggested keyword chips.
- **Unified feed** — filter by platform, keyword, status and free-text search; paginated cards with intent score, relative time and a link to the original post.
- **Channel selectivity** — enable/disable individual platforms per workspace; disabled channels are skipped server-side so no API call is made for them.
- **Intent filtering** — configurable minimum intent score, applied server-side before anything is stored.
- **AI outreach drafter** — personalised reply drafts in four tones, generated by GPT-4o-mini.
- **Exports** — CSV (Excel-safe, with a UTF-8 BOM) and JSON.
- **Webhook alerts** — Slack/Discord webhook with a real test-ping button.

---

## 🛠 Tech Stack

- **Frontend**: React 19, TypeScript, Vite, Tailwind CSS v4, Framer Motion, Lucide React, canvas-confetti.
- **Backend**: Supabase (Postgres, Auth, Edge Functions, RLS).
- **Edge Functions**: `social-search` (treg), `ai` (OpenAI), `billing` (Stripe), `daily-sweep` (cron).

## ⚡ Quick Start

### 1. Install & run
```bash
npm install
npm run dev
```
Open [http://localhost:5173](http://localhost:5173).

With no Supabase credentials the app runs in a **local sandbox** using `localStorage` — useful for UI work.

### 2. Connect Supabase
Copy `.env.example` to `.env` and fill in:
```env
VITE_SUPABASE_URL=https://<your-project-ref>.supabase.co
VITE_SUPABASE_ANON_KEY=<your-anon-key>
```

> **Never put secret keys in `.env`.** Any `VITE_`-prefixed variable is inlined
> into the public JS bundle. The treg, OpenAI and Stripe keys live in Edge
> Function secrets — see [Secrets](#secrets) below.

### 3. Apply the schema
**Easiest:** Supabase Dashboard → SQL Editor → paste the whole of
[`supabase/deploy-all.sql`](supabase/deploy-all.sql) → Run.

It contains every migration concatenated in the correct order and is safe to
run twice (everything is `IF NOT EXISTS` / `IF EXISTS` / `OR REPLACE`).

**Or** run the numbered migrations in order:

| File | Purpose |
|---|---|
| `20250101000000_echo_schema.sql` | `profiles`, `keywords`, `monitored_posts`, `sweep_runs` + RLS + triggers |
| `20250102000000_add_enabled_channels.sql` | `profiles.enabled_channels` |
| `20261017_security_hardening.sql` | Plan-aware keyword limit, `min_intent_threshold`, server-column guard, `apply_subscription_plan` |
| `20261018_remove_credits_system.sql` | Drops `lead_unlocks`, `credit_transactions`, `profiles.credits_balance` |
| `20261019_security_lint_cleanup.sql` | Advisor-driven fixes: RPC revokes, `(select auth.uid())` policies, FK index |
| `20261020_backfill_and_constraints.sql` | Re-scores existing posts onto the current 0–97 scale; adds `CHECK` constraints on channels + threshold |
| `20261016_lead_selling_credits.sql` | ⚠️ **Legacy only.** Upgrade path for a database that still has the credit tables. Do not run on a fresh install. |

> **Backup before running Section 4** — it permanently deletes
> `lead_unlocks` and `credit_transactions`.

### 4. Set Edge Function secrets
```bash
supabase secrets set TREG_TOKEN=treg_your_token     # https://treg.to — free signup, $1 credit
supabase secrets set OPENAI_API_KEY=sk_your_key
supabase secrets set STRIPE_SECRET_KEY=sk_live_your_key
supabase secrets set APP_ORIGIN=https://your-app.example
supabase secrets set SWEEP_CRON_SECRET="$(openssl rand -hex 32)"
```
`SWEEP_CRON_SECRET` and `TREG_TOKEN` may also live in `public.service_secrets`
instead, which is what the scheduled-sweep setup in step 6 uses. The edge secret
wins when both are present.

### 5. Deploy functions
```bash
supabase functions deploy social-search
supabase functions deploy ai
supabase functions deploy billing
supabase functions deploy daily-sweep --no-verify-jwt
```

Without `STRIPE_SECRET_KEY`, `billing` refuses every request, so plan changes
are unavailable. It never falls back to granting access for free.

### 6. Schedule the sweep
Without this, **nothing sweeps automatically** — the Run sweep button is the
only way to collect. `pg_cron` fires hourly and `pg_net` makes the call; each
workspace is swept in the UTC hour it set in Settings, so "every day at 06:00
UTC" is literally true while each account still sweeps once per day.

```sql
-- One-time: generate the gate secret (32 random bytes, hex).
insert into public.service_secrets (name, value)
values ('sweep_cron_secret', encode(gen_random_bytes(32), 'hex'));

-- Then schedule. The secret is read at fire time rather than baked into the
-- command, so there is a single place to rotate it.
select cron.schedule(
  'echo-daily-sweep',
  '0 * * * *',
  $$ select net.http_post(
       url     := 'https://<project-ref>.supabase.co/functions/v1/daily-sweep',
       headers := jsonb_build_object(
         'Content-Type',  'application/json',
         'x-sweep-secret', (select value from public.service_secrets
                            where name = 'sweep_cron_secret')
       ),
       body    := '{}'::jsonb,
       timeout_milliseconds := 180000
     ); $$
);
```
`supabase/migrations/20261023_scheduled_sweeps.sql` does all of this.

## 🔒 Security model

| Concern | How it is handled |
|---|---|
| Vendor API keys | Held only in Edge Function secrets; never in `.env` or the bundle |
| Subscription state | Server-only. `subscription_plan` / `_status` / `_renews_at` are blocked from client writes by both a column grant and a trigger |
| Plan changes | Applied only via `apply_subscription_plan` (service-role only), invoked by the Stripe-verifying `billing` function |
| Sweep function | Requires the `x-sweep-secret` header — not publicly invokable |
| Edge functions | Verify the caller's JWT and derive identity server-side; per-user rate limits |
| Keyword limits | Enforced by a Postgres trigger from the user's plan, not just the client |
| Webhook URLs | Validated against Slack/Discord host allow-list |

---

## 💳 Billing

Plans are defined in two places that must stay in sync:
- Client: `src/lib/billing.ts`
- Server: `public.plan_keyword_limit()` in `20261017_security_hardening.sql`

Plan changes go through Stripe Checkout. A plan is activated only after the
`billing` function confirms `payment_status === 'paid'` and that the session was
created for the calling user.
