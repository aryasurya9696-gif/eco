## Executive summary

**The core ledger is sound.**
- `wallet_reserve` / `wallet_settle` / `wallet_release` keep `balance = Σ grants`.
- Grants are drawn FIFO.
- Holds are row-locked.
- Every money RPC is `service_role`-only with a pinned `search_path`.
- Webhook signatures are verified correctly.
- No IDOR or cross-tenant leak was found in any edge function.

**What fails is everything around the ledger:**

1. **Money leaks out through edge cases.**
   - Webhook replay re-grants refunded orders (C3).
   - A full revoke revoked **nothing**, so chargebacks left credits in place (N2).
   - Sweep wrappers ignored RPC results, so sweeps ran free (H2).
   - Leads holds can never be settled by the reaper (H6).
2. **One sweep bug may be overcharging customers right now (N1).** `daily-sweep` selects the dropped column `profiles.subscription_plan` and discards the error. With no settings loaded, every workspace with active keywords counts as *due every hour*. If the hourly cron is live, each workspace is swept and charged **24× a day** on default channels: up to 32 credits × 24 = 768 credits ≈ $36 per day. **This needs the read-only check in E.2(h) first.**
3. **Leads pricing loses money.**
   - A 1-credit people search can make 11–12 provider calls at up to $0.05 each.
   - Email and phone credits sit at about 15 % margin even at a 100 % hit rate, and go negative below about 85 %.
   - 20 welcome credits can buy up to about $11 of provider spend through 20 large searches.
4. **The schema file could not run at HEAD** (C1, C2). It is fixed in WT: the Phase 1 session reports that `deploy-all.sql` now applies fresh and re-applies cleanly on PGlite.
5. **The Mail composer faked AI at HEAD** and inserted Echo's own marketing claims into users' emails (H8). It is being replaced in WT.

**Ten Critical/High items that are still open even in WT:**
- N1 (sweep schedule ignored)
- H3, H4, H11 (leads economics)
- H5 (bulk reveal double charge with nothing saved)
- H6 (reaper vs leads)
- H7 (non-atomic revoke)
- M4 (mail SMTP SSRF)
- M8 (owner-readable cost columns)
- the unverified pricing itself

## D. Billing audit

### D.1 Wallet invariants: what holds

- **Reserve.** `wallet_reserve` locks the wallet row `FOR UPDATE` and refuses when `balance − reserved < needed`. It is idempotent on `reservations.idempotency_key`.
- **Settle.** `wallet_settle` requires `status='held'`, clips the charge to `credits_held`, draws grants FIFO and writes a ledger row with revenue Σ take × unit price.
- **Release.** `wallet_release` returns the hold and writes no ledger row.
- **Permissions.** All are `security definer`, `search_path` pinned, and granted to `service_role` only. V (DB pass, awk scan of all 43 functions).

```sql
-- cost per attempt and hit rate (a2, abridged)
select operation, count(*) attempts,
       count(*) filter (where credits_charged > 0) billed_hits,
       round(count(*) filter (where credits_charged > 0)::numeric / nullif(count(*),0), 4) hit_rate,
       round(sum(provider_cost_usd) / nullif(count(*),0), 6) cost_per_attempt_usd
from public.api_usage
where operation in ('treg.people.search','leads.search','treg.people.email.find','treg.people.phone.find',
                    'treg.twitter.search','treg.reddit.search','treg.web.search','treg.news.search')
group by operation order by operation;

-- is the guard trigger still live? (c)
select tgname from pg_trigger where tgname = 'trg_profiles_server_columns';
```

### E.4 Credits needed for ≥ 60 % margin

**Formula** (from the plan):

```
credits per billed use = ceil( (avg cost per attempt ÷ hit rate) ÷ (net $ per credit × (1 − 0.60)) )
                       = ceil( cost per billed use ÷ 0.01874 )       ($50 pack, intl)
```

| Feature | Cost per billed use used | Required credits | Now | Change |
|---|---|---|---|---|
| X search | $0.00075 (cap $0.01) | **1** | 1 | none |
| Reddit search | ≤ $0.02 (both calls at cap) | **2** | 2 | none; stop the fallback when tikhub *billed* (N9) |
| Web search | $0.00015 (cap $0.01) | **1** | 1 | none |
| News search | $0 | **1** (any) | 1, but 0 charged | fix N9 so the configured credit is actually charged, or price it at 0 and label it "Free" consistently |
| People search, per billed provider call | $0.05 | **3 per call** | 1 per search | charge per billed call, or base 3 + **`leads.search.extra_50` = 2** (≈ $0.025 of provider cost per 50 leads → ceil(1.33)) |
| Verified email (h = 1.0 / 0.7 / 0.5 / 0.3) | $0.040 / 0.057 / 0.080 / 0.133 | **3 / 4 / 5 / 8** | 1 | set from measured h |
| Direct phone (h = 1.0 / 0.7 / 0.5 / 0.3) | $0.08 / 0.114 / 0.16 / 0.267 | **5 / 7 / 9 / 15** | 2 | set from measured h; also verify numbers before charging |
| Mail, hosted | $0.0004 variable | **0.05** (0.0213, rounded up to the 0.05 step) | 0.1 | keep 0.1; it also covers a Resend fixed fee at about 13.6k sends/month (see below) |
| Mail, connected | $0 | > 0 | 0.05 | keep |
| AI | ≈ $0.0005/call (estimate, UNVERIFIED) | 0 is acceptable only with tracking | 0 | write `api_usage` rows so the cost becomes measurable |

**Resend fixed fee**
- At 0.1 credit per hosted send, each send leaves $0.00147 after the 60 % target and the $0.0004 variable cost.
- A $20/month plan therefore needs about **13,600 hosted sends a month** to stay at 60 %.
- The Resend plan price is **UNVERIFIED**.

**People search: two pricing options**
- (a) Charge **3 credits per billed provider call**. This is exact, because the code already counts calls through `usage.costSince`.
- (b) A base of 3 credits plus 2 credits per 50 leads beyond 25.
  - At 25 leads: 3 credits ($0.141) against $0.05 → 64 %.
  - At 1,000 leads: 3 + 20 × 2 = 43 credits ($2.01) against $0.55 → 73 %.
  - Option (b) under-charges when many calls return few rows, so **(a) is recommended**.

Every change above is a data edit in `pricing_config`; no deploy is needed. **No price was changed by this audit.**
